A small GPT, built from scratch

Writing the transformer behind modern language models in PyTorch, and training it on a laptop to imitate Shakespeare.

Alexander Gilbreath  ·  machine learning, personal project

I had been using language models through an API for a while without really knowing what happens inside one, so I set out to build a small one myself, from the attention math up. The result is a 30-million-parameter GPT I wrote in PyTorch and trained on Shakespeare until it could produce dialogue in roughly the right shape: character names, line breaks, the archaic phrasing. What follows is how it works and what I found while building it.

The model

It is a decoder-only transformer, the same family of architecture the GPT models use. Instead of downloading a model or fine-tuning an existing one, I implemented each piece: the token and positional embeddings, the multi-head causal self-attention, the feed-forward layers, and the layer normalization that keeps training stable. Stacked six layers deep, it comes to just over thirty million parameters.

The point was to stop treating a language model as a black box. Having written the components, I can now say exactly how text becomes numbers, how the model looks across a sequence, and how it learns to predict what comes next.

How it reads a sequence

Text comes in as tokens and moves upward through the six transformer blocks. Inside each block, attention lets every token look back over the tokens before it and weigh which ones matter for predicting the next. That attention is causal: a token can only see what came earlier, never the word it is trying to predict. The restriction is what forces the model to learn the language instead of copying the answer.

tokens → embeddings → attention + feed-forward ×6 → next-token prediction

Training it

I split the work into separate scripts so the whole run is reproducible. First the text is tokenized with GPT-2's byte-pair encoding and split 80/20 into training and validation sets, roughly 294,000 and 75,000 tokens. Then the model trains with an AdamW optimizer against a cross-entropy loss, logging both losses at intervals and saving checkpoints as it improves. A final script loads a checkpoint and generates text from a prompt, so I can read back what it actually learned.

Did it learn?

Training loss dropped from 6.11 to 3.87. By itself that number means nothing; the useful comparison is the baseline. Guessing randomly across a 50,257-token vocabulary scores about 10.8, so reaching 3.87 means the model found real structure in the text rather than memorizing noise.

Validation loss finished a little above training loss. That is the mild overfitting you would expect from a thirty-million-parameter model trained on only about 300,000 tokens, and more data or a smaller model would narrow it. The generated samples confirmed the result on their own, with recognizable character names and correctly formatted dialogue that nothing in the code told it to produce.

The part that was actually hard

The model trained without much trouble. Getting it to train fast enough to experiment with was the real problem. My laptop has no NVIDIA GPU, so CUDA was off the table and everything ran on Apple's MPS backend, where performance behaves differently. Early steps took around two seconds each, too slow to iterate on.

Rather than guess at fixes, I profiled a single step and traced almost all of the cost to the final softmax over the 50,257-token vocabulary, the most expensive operation on this backend. Lowering the batch size to sixteen fit the backend better and brought a full run down to about eleven minutes, without changing the architecture or the result. Finding out why it was slow before changing anything is the part I am most pleased with, and it is the difference between a model that happens to run and one I understand.

What I took from it

Building this closed the gap between using language models and understanding them. I can explain what attention does, why the loss falls, and where the compute goes, because I wrote each of those parts rather than importing them. It also walked me through the full shape of a real machine-learning project: preparing data, defining a model, training and evaluating it, generating from it, and profiling the slow parts in between.
